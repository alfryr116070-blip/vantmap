# Vantmap 流程 v2：三层分级 + 发现层 + 有事才核查

版本 2.1（2026-11-24，按独立评审意见修订）。子任务提示词模板在 prompts/。docs/daily.md 和 docs/new-map.md 以本文件为准，有冲突时按本文件；没提到的规则照旧（rubric.md、零错误标准、存档、标注库、翻译）。

## 一、三层分级

| 层 | 数据位置 | 放什么 | 我们保证什么 | 核对方式 |
|---|---|---|---|---|
| 第一层 主图 | map.json `entries` | 正面在做这件事、有 C 级以上证据的团队 | 阶段、证据、资金、产品、公开成果全部零错误 | 写稿 → 两路独立判断 → 抽样验收 |
| 第二层 观察名单 | map.json `watch` | 相关但较小、偏一点、或还没做完整核对的团队 | 只保证：团队存在；一句话描述和来源网页一致 | 写稿 → 一路判断 → 抽样验收（每次建图抽 20 条） |
| 第三层 线索 | map.json `leads` | 信息流抓到、还没打开核对的链接 | 不作任何判断，只列标题、来源、日期 | 不核对 |

- 页面上的统计（团队数、最远阶段、到达终点数、活跃数）、AI 解读、竞争压力、体量集中度只用第一层。
- 第二层的 `stage_rough` 只写“粗判 Sx”，不进任何统计。**粗判必须按本图的阶段定义（project.domain_rules）判**，并且要判它和本图目标的关系（例如只做到目标一部分的产品，不算目标本身的 S2）；拿不准写 null，页面就不显示阶段。验收必须检查粗判阶段。
- 第二层的一句话里出现**金额、估值、监管结论（批准、加速批准、日期）或自报性能数字**时，这句话按关键结论处理：必须另派一个没写过它的 opus 子任务联网核对，通过后写 `key_checked: 日期`；check.py 会拦下没有 key_checked 的条目。`why` 只写“为什么不在主图”的事实依据（阶段、适应症、方向偏差、核对范围），不写“规模小”这类没有来源的判断。
- 第三层不写任何结论性文字。标题用原文标题；`title_zh` 只能是标题的直译。

### 数据结构

```
watch: [{id, name, short, branch, stage_rough: "S0".."S3"|null, one_line, why, key_checked?,
         sources: [{url, quote, grade, date, verified, archive}], checked, added}]
leads: [{id: "l-…", title: 原文标题（降级条目用团队名并设 title_is_name:true，不带任何说明）, title_zh?, url, source: 信源名或域名, date, found, matched: 条目id|null, branch_guess, note?: 状态说明, title_is_name?}]
project.sources: [{id, name, url, kind: "blog|news|releases|arxiv|journal|registry|other",
                   covers: [条目id...], lang, note}]
```
`data/maps/<id>/feed.json`：`{last_run, seen: {url_hash: date}, titles: {norm_title: date}}`（发现层的去重状态，只增不删，保留 180 天）。

### 升降规则（写死）
- 第三层 → 第二层：打开后找到 C 级以上来源，且和目标相关。
- 第二层 → 第一层：通过完整核对（写稿 + 两路判断），并有支撑阶段的 C 级以上证据。
- 第一层 → 第二层：证据被推翻；或超过 18 个月没有实质进展且已不贴合目标；或核对后发现不在这张图的范围里。
- 第三层删除：90 天内没有升层的线索删除（feed.json 仍记着，不会再进来）。
- 每次升降在 `changes` 追加一条，type 为 `promote` / `demote` / `watch`。

## 二、每日流程（每张地图）

### 步骤 A 发现层（便宜）
0. 一张图第一次跑（没有 feed.json）时，feed.py 进入**基线模式**：只记录信源上现有的条目，不产生命中，避免把旧条目全部当成新消息。
1. 读 `project.sources`。每 10 个信源派 1 个 haiku 子任务，**只用 WebFetch 打开给定网址，不用 WebSearch**。
2. 子任务对每个信源列出窗口内（SINCE = feed.json 的 last_run 往前 2 天）的新条目：`{url, title, date, source_id, relevant: true|false, why}`。`relevant`：只有讲**本图方向的方法或产品本身进展**的条目才算 true；纯学科研究、通用大模型新闻、算力、行业活动、获奖新闻一律 false；拿不准写 true（模板见 prompts/discover_prompt.md）。
3. 运行 `python3 feed.py map.json feed.json items.json T hits/ [--since D] [--max-hits 25]`：
   - 按网址去重，再按（信源, 标题）去重；短标题（如版本号）只按网址去重；
   - 有完整日期且早于窗口的丢弃；没有年份的标为 undated，起草时必须先在带年份的页面确认日期，确认不在窗口内的判为“已记录/旧条目”；
   - 常见词名称（如 Atlas、Nova、Orbit）单独出现不算命中，只认全名或信源归属；
   - 每天命中最多 25 个（第一层、有日期的优先），超出的留到第二天；
   - 相似标题聚成一个事件（同一件事多个来源只算一次）；
   - 按条目的 name / short / aliases 匹配第一层和第二层；
   - 输出 `hits.json`、`newleads.json`、`sweep.json`、`overflow.json`。
   - **只有当天的结果处理完并发布成功后**，再用同样参数加 `--commit` 跑一次，才会把见过的网址写回 feed.json；中途失败就不写，第二天会重新看到这段窗口。

### 步骤 B 兜底轮查（防漏报）
- 第一层：每天轮查 1/7 的条目（`feed.py` 按 id 哈希和日期算出今天该查谁），保证每个条目每周至少被直接搜一次。haiku，每个 1 次 WebSearch。
- 第二层：每 30 天轮一遍（每天约 1/30）。
- `project.sources` 里 `covers` 为空的条目，每 3 天查一次。
- 兜底发现的新动态，和命中一样进步骤 C。

### 步骤 C 命中核查（只在有事时花钱）
对每个命中事件：
1. **抓取并起草**（sonnet，1 个子任务可处理 3 个事件）：打开网址一次，把包含关键内容的原文段落逐字存进 `cache/<url_sha>.json`（`{url, fetched_at, title, published, passages:[...]}`），再按 rubric 起草改动：新证据 `{grade, date, text, url, quote, progress}`、里程碑、阶段建议。**quote 必须是 passages 里的逐字子串。**
2. **机器检查**：`python3 cache_check.py drafts.json cache/` 检查每条 quote 是否逐字出现在缓存段落里、日期是否在段落里出现过同样精度。不通过的退回第 1 步，不进判断。
3. **两路判断**（opus，**不联网，只读缓存段落**）：两个子任务分别用不同问法判断“结论 + 原文段落”是否一致，输出 正确 / 小误差 / 错误 / 没有依据。两路都判正确才写入；有一路判小误差的，按修正改完后**必须再判一次**（另派一路 opus 判断，或由联网抽查逐条核对改后的文字）通过才写入；不一致的派第三个 opus 子任务按 rubric 规则编号仲裁；仲裁仍不确定的进 `human_queue`。判断标了 `needs_online` 的条目一律联网核对。
4. 第二层条目命中时只做一路判断，可改的只有：补一条来源（source_add）、改 one_line（one_line_new，涉及金额/监管/自报数字的按关键结论再联网核对）、改粗判阶段（stage_rough_new，按本图阶段定义）；满足升层条件的走第一节的升降规则。
5. **联网抽查**：当天写入第一层的新结论，按 20%（至少 1 条）随机抽取，另派一个没参与的 opus 子任务联网打开原网页核对；有一条不正确，当天写入的全部改为联网逐条核对。原因：缓存原文来自抓取工具的返回（可能是摘录或转述），离线判断只能证明“写的和抓到的一致”，证明不了“和网页一致”。
6. **写入后同步全条目**：写入一条第一层新结论后，必须把同一条目的所有文字和数字字段逐个扫一遍——product（intro、status、sources）、funding（last_round、total_usd、valuation_usd、note、sources、cites）、milestone、note、gaps、impact、relation——凡是被新证据推翻或过时的（如“待定”“pending”“未完成”“未确认”“尚未”），当场改写并换上新来源；资金事件必须同时更新 funding（last_round 写成 {date, name, amount_usd, valuation_usd} 对象）。起草子任务按 hit_draft_prompt 给出 funding_update / product_status_new / field_updates，判断时一并判。check.py 会对最近一次核对日有新核对证据的条目里出现这些词给出提醒，提醒必须逐条看过（机器提醒只是兜底，主要靠这一步人工扫描）。第一层当天有写入的图，当天重写 AI 解读（提示词 prompts/brief_prompt.md）。
7. 所有判定写进标注库（round 用 `hit:T`）。

### 步骤 D 线索
- `newleads.json` 追加进 `leads`（只存标题、来源、日期、网址、branch_guess），不打开、不核对。
- 每天另派 1 个 sonnet 子任务挑 5 条最新、看起来最相关的线索打开核对：有 C 级以上来源的升入第二层（按第三节写观察名单条目，并做一路判断）；不相关的删除。注意：公司自己的官方页面（含产品功能页）是 B 级，不是 D 级；D 级只给聚合站、转载、招聘帖和第三方营销稿。

### 步骤 E 其余照旧
派生里程碑、check.py、翻译（haiku，翻完抽 10 对检查错位，并检查公司名有没有被换成别家）、存档、标注库、发布，然后 `feed.py … --commit`。每周一的抽查、金丝雀、漏报检查照旧；第二层每周一每张图抽 20 条联网核对（含粗判阶段）。

## 三、建新图（详细步骤见 docs/new-map.md）

1. **摸底**：同 5b（深度研究初稿 + 补漏 + 漏报检查），但最后把名单分三档：主图候选（正面在做、规模或进展足以比较）、观察名单候选、线索。
2. **信源清单**：派 1 个 sonnet 子任务为这张图列 20–60 个固定信源（各团队官方新闻页 / 博客、GitHub releases 页、相关 arXiv 分类列表页、行业媒体栏目），每个写清 `covers`。只列能直接打开的网址。
3. **主图条目**：每个团队 1 个 sonnet 子任务写条目，规则见第五节。所有引用的网页同时存进 `cache/`。
4. **机器检查** `cache_check.py`，不通过的退回。
5. **两路判断**：opus，不联网，只读缓存段落；每个子任务判 30–40 条。
6. **观察名单**：每 10 个团队 1 个 sonnet 子任务，每个团队打开 1–2 页，写 `one_line`、`why`、`stage_rough` 和一条带逐字 quote 的来源；1 个 opus 子任务一路判断。
7. **验收**：第一层随机抽 50 条；第二层条目不超过 25 条时全量核对，超过时抽 20 条，由没参与的 opus 子任务**联网打开原网页**核对（含粗判阶段）。标准：0 错误、小误差 ≤ 2/50（第二层 ≤ 1/20）。修正后重验时，新一轮必须抽**没抽过的**条目。最多 3 轮。
   - 统计说明：20 条全对时，按“三法则”错误率的 95% 上限约 15%，50 条全对约 6%，都证明不了“≤ 4%”。验收只是门槛；真正支撑零错误标准的是第二路联网核对、每日联网抽查和每周抽查的长期累计，页面上按累计数字报告。
8. 翻译用 haiku；其余按 docs/new-map.md 第 5e–7 步。

## 四、模型分配

| 工作 | 模型 | 理由 |
|---|---|---|
| 发现层抓取、兜底轮查、翻译 | haiku | 机械工作，错了有后续核对兜底 |
| 摸底初稿、写条目、抓取起草、观察名单 | sonnet | 要理解和归纳，但最终对错由别人判 |
| 两路判断、仲裁、验收、阶段判定 | opus | 决定可信度的环节，不省 |

## 五、写作规则（来自 11-19、11-20 两张图的验收失分）

1. **年份**：只有在打开的网页上看到带年份的日期才能写年份。发布页只显示“21 Apr”的，必须另开一个显示年份的页面（如 PyPI 发布历史），并把它也列为来源。
2. **日期格式**：DD/MM 和 MM/DD 拿不准的，看同站其他日期判断，并在 note 写明依据。
3. **quote**：必须是缓存段落里的逐字子串，由 `cache_check.py` 检查；不写拼接句，不写概括句。
4. **不写推断**：evidence 的 text 只写原文有的内容。“没提到 X”“不是 X”这类判断写进 `note` 或 `gaps`，不写进 evidence。确实要写时写成“打开的页面未提到 X”。
5. **单位和作者**：只写页面上看得到的作者单位；看不到就不写。
6. **措辞强度**：计划、称、约、预印本、工作坊论文照原文写；表格里推算出的数字要写“按表中数字推算”。
7. **许可证**：必须打开 LICENSE、模型卡或论文页的许可证标注；论文的许可证和代码的许可证分开写。
8. **一条证据只说一件事**，便于判断和后续修改。

## 六、成本记录
成本只按真实计费数字报告（子任务结果里的 usage 或账单），不对外引用估算值。比较新旧流程时按“每条被核实的结论”的成本比较，并把主会话自身的读写、两路判断、每周抽查、建图分摊都算进去。
`project.run_stats` 每次追加 `{date, by_model:{haiku:n, sonnet:n, opus:n}, searches, fetches, hits, leads_new, minutes}`。每周一的消息汇总一周的子任务数（按模型分）。
